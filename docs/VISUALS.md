# K.O. Tool — Visuals (product specification)

**Status:** owner-approved direction, 17 October 2026. **Visuals is not implemented in `main`.** This document describes intended behavior, not authorization to change application code.

## Product role and placement

- **K.O. Tool** is the **browser-based virtual desktop** and product; **Visuals** will be a **separate app with its own icon inside that virtual desktop** (earlier owner choice A for app placement). It is **not** a native macOS/Windows app or an icon on the host operating system's desktop.
- Visuals is **not** a tab or panel inside My EP. The sequencer stays at `My EP → Projects → Sequencer` and requires a connected EP for project access.
- Goal: make live performances and on-camera sessions visually engaging with audio-reactive graphics. **Owner-approved default presentation:** a long, low-profile **meter dock strip along the bottom edge** of the K.O. Tool browser viewport (owner choice B); not a large conventional app window. This resembles the overall arrangement in the owner's supplied concept image, but is not a mandate to copy any existing product. Exact sizing and optional **in-browser** performance views remain separate decisions; host-OS overlays/windowing are **outside the chosen product scope**.
- Reference for independent design research: [MiniMeters](https://minimeters.app/). Do not copy proprietary branding, code or graphic assets.

## Bottom meter strip — owner-approved layout and v1 modules

**Default layout (owner choice B):** a continuous horizontal **Visuals meter strip across the bottom** of the available K.O. Tool viewport, intended to stay visible while using My EP and for filming hardware performances. The width should follow the available screen/viewport; ensure readability at realistic desktop widths.

**First-version module scope (owner choice C, seven distinct modules):**

1. **Waveform** — incoming time-domain audio shape.
2. **Spectrum** — frequency-domain energy distribution.
3. **Loudness** — visible loudness level readout/meter; exact algorithm (e.g. LUFS) requires separate technical specification and verification.
4. **Stereo Meter** — stereo imaging/correlation visualization, only when input channels provide meaningful stereo data.
5. **Output Meters** — channel level/peak display for the audio being analyzed; **this does not imply browser capture of the system's output**.
6. **Oscilloscope** — detailed time-domain trace; distinct display mode from overview waveform.
7. **Spectrogram** — frequency energy over time.

All seven are **approved as the v1 feature set** and must remain available for selection. **Initial Balanced layout (owner-approved option C)** displays all seven modules when space permits. Users may subsequently hide/restore individual modules. Input-channel limitations should be explained honestly (e.g. mono input does not provide stereo spread).

### Default Balanced composition (owner-approved)

- **Large / prominent:** **Waveform** and **Spectrum** receive the most horizontal emphasis.
- **Medium:** **Spectrogram** receives moderate space.
- **Compact:** **Loudness**, **Stereo Meter**, **Output Meters**, and **Oscilloscope** are smaller but readable.
- The default must preserve the seven-module scope and never violate the responsive sizing rule: on narrow screens, shrink only to usable minimums and then **scroll horizontally**, not hide modules automatically.
- **Initial/fallback left-to-right Balanced module order — owner choice A (approved), overridden at subsequent openings by a valid last-working-layout snapshot (question 57 choice C):** **Waveform → Spectrum → Spectrogram → Loudness → Stereo Meter → Output Meters → Oscilloscope**. This ordering is the approved **startup/default Balanced arrangement**, not the numbered feature-inventory list above. Show all seven modules and preserve the previously approved prominence: Waveform/Spectrum large, Spectrogram medium, and the four remaining meters compact.
- **Reordering remains user-controlled:** users may drag any module to a new position and save/restore their own browser-local layouts. Restoring the built-in **Balanced default** returns to the approved order without overwriting custom presets. Do not silently reorder on viewport resize; use the approved width shrink and horizontal scrolling.
- **Approved Balanced width proportions — owner choice A:** with all seven modules present and enough horizontal room, use **Waveform 25%; Spectrum 25%; Spectrogram 18%; Loudness 8%; Stereo Meter 8%; Output Meters 8%; Oscilloscope 8%** in the approved left-to-right order. **Check: 25 + 25 + 18 + (4 × 8) = 100%.** These percentages describe the initial Balanced *relative widths*, not seven fixed pixel values; do not apply them as hard minimums.
- **Responsive and customization precedence:** respect separately selected user module widths / saved custom layouts. When the window is too narrow for readable modules, follow the existing approved responsive policy: shrink proportionally only to safe per-module minimums, then enable horizontal scrolling; never silently hide/reorder modules, cut off controls or overwrite stored preset widths. **Manual hiding and its approved proportional redistribution** are separate from automatic responsive behavior.
- **Owner-approved minimum module widths — choice B:** **Waveform 200 CSS px; Spectrum 200 CSS px; Spectrogram 160 CSS px; Loudness 96 CSS px; Stereo Meter 96 CSS px; Output Meters 96 CSS px; Oscilloscope 96 CSS px.** With all seven visible, the minimum **sum of the module widths is 944 CSS px** (200 + 200 + 160 + 4 × 96), **excluding** module gaps, borders, strip controls and padding.
- **Width precedence:** the 25/25/18/8/8/8/8 percentages are the *target proportions* only where all minimums fit. When a compact module's 8% share would be less than its 96 px minimum, respect the minimum instead and adjust the remaining available widths without changing order. If the sum of the visible modules' minimum widths **plus actual layout spacing and controls** cannot fit, use **horizontal scrolling** rather than shrinking any module further, hiding it or silently changing stored custom widths. The **owner-approved question 49 choice A** now defines how free space is distributed when minimum widths bind; implementation-specific rounding, measured spacing and actual breakpoints still require verification. Native browser scrolling is separately approved below.
- **Proportional allocation with clamped minima — owner choice A (question 49, approved):** if one or more visible modules need their approved minimum CSS width, keep those modules at that minimum and distribute **all remaining usable module-content width among the other visible modules in proportion to their original intended width ratios** (built-in preset or unsaved in-session/user-defined ratios). If another module's resulting share falls below its minimum, clamp that module too and redistribute the still-available width proportionally among the others; continue respecting every module minimum. Do **not** distribute equally by module count or prioritize Waveform/Spectrum/Spectrogram merely because of their type. Example: for Balanced at **980 CSS px of usable module-content width, excluding gaps/padding/controls**, the approved result is **Waveform 218, Spectrum 218, Spectrogram 160, Loudness 96, Stereo Meter 96, Output Meters 96, Oscilloscope 96 CSS px** (total 980). At **less than 944 CSS px of usable module-content width**, seven minimums cannot fit; preserve all seven minima and expose horizontal scrolling rather than violating them. This is **responsive/proportional space allocation**, not manual divider dragging: the separately approved equal-and-opposite adjacent-visible-pair-only drag rule remains intact. Never write temporary rendered sizes back to underlying intended ratios or silently overwrite browser-local named presets; recompute from intended values on viewport/module visibility changes without rounding drift.
- **Proportional redistribution when manually hiding modules — owner choice A (approved):** if one or several modules are deliberately hidden, **expand the remaining visible modules to use the freed horizontal space proportionally to their existing intended widths**, preserving their relative width ratios and current left-to-right order. This rule applies to Balanced, built-in workflow layouts and user-arranged layouts; for the standard Balanced widths, hiding **Spectrogram (18%)** redistributes the available width among Waveform/Spectrum (25 units each) and the four 8-unit meters (82 units total), subject to minimum widths.
- **Restoring modules and preset protection:** hidden modules remain available to restore with their original intended widths/settings. Proportional growth for the *visible presentation* is **not** an instruction to overwrite the hidden module's width, permanently change saved preset widths or compound the temporary expanded percentages after successive hide/show operations. When a module is shown again, recompute from the underlying intended widths, not from rounded/intermediate expanded rendered widths. Only explicit Save actions may update a **named** user layout; question 57 choice C separately approves auto-saving the **unnamed current working-state snapshot** without overwriting any named preset.
- **Responsive precedence:** expand to fill free space **where that space is usable**; do not violate the already approved 200/200/160/96×4 CSS-px module minimums, force a fit when visible minimum widths plus spacing overflow, or eliminate required horizontal scrolling. Allocation with clamped minima follows question 49 choice A above (original intended ratios among unclamped visible modules); manual width changes with hidden modules follow the separately approved visible-pair-only rule below, and native scrolling follows choice B. Pixel rounding remains an implementation verification detail.
- **Manual module width resizing — owner choice A (approved):** dragging a module's right-hand shared divider adjusts its width and changes **only its immediately adjacent visible module to the right** by the opposite amount. For example, increasing Waveform width by 40 CSS px decreases neighboring Spectrum width by 40 CSS px; other visible modules keep their intended widths. Reversing the drag reverses the pair adjustment. This is distinct from the approved proportional expansion of all remaining modules after a user deliberately hides one.
- **Guardrails:** retain the approved minimum widths of **both** affected modules (Waveform/Spectrum 200 CSS px each, Spectrogram 160 CSS px, remaining four meters 96 CSS px each); no automatic reordering/hiding, cascading changes to unrelated modules or silent overwriting of browser-saved presets. A manually adjusted custom layout may be saved only through the existing explicit preset-save workflow.
- **Manual resize while some modules are hidden — owner choice A (approved):** with **two or more visible modules**, dragging the shared divider updates the **intended widths of only the two immediately adjacent visible modules at that divider**, equally and oppositely in the rendered pair, subject to their minimums. **Hidden modules do not participate and their intended widths/settings never change**. For example, when Spectrum is hidden, dragging the boundary between visible Waveform and Spectrogram edits only those two; it must not affect Spectrum or any other visible module.
- **Persisting the pair edit with hidden modules — owner question 50 choice A (approved):** save the **post-drag ratio of the two edited visible modules**, not a permanent +/− CSS-pixel offset and not a percentage of the full strip. Derive the ratio from the pair's actual **rendered widths after the divider moved** (respecting approved minimum-width clamping and the stop-at-minimum behavior). Update the pair's **underlying in-session intended widths** in that ratio while preserving the pair's **combined underlying intended-width weight**; every hidden module and every other visible module keeps its previous intended width. For example, if rendered Waveform/Spectrogram widths become **440:260 CSS px** after a valid drag while Spectrum is hidden, their new underlying ratio is **22:13**. If their pre-drag intended widths sum to **500 width units**, they become **500×22/35 ≈ 314.286** and **500×13/35 ≈ 185.714** units, with the hidden Spectrum's intended width untouched. These width units are relative layout weights, **not a promise of the same displayed pixels after a hidden module returns**. Re-showing Spectrum or resizing the viewport recomputes displayed widths from the stored intended weights via question 49's minimum-aware proportional allocation; clamped minima can cause temporary rendered ratios to differ, but must not overwrite the intended **22:13** ratio. Reverse drags and repeated hide/show should avoid compounded rounding drift; no browser-local named preset updates without explicit Save. For a drag where the pointer asks to pass the pair minimum, record the **clamped actual end widths**, not the illegal pointer target. This describes the approved user-visible semantics; precise representation, CSS-subpixel rounding and edge-case implementation still require validation.
- **Returning hidden modules after manual edits:** preserve the user's *unsaved in-session* pair edits when revealing Spectrum or another hidden module; recompute visible proportions from the edited intended widths of the touched pair **plus the untouched underlying intended widths of hidden and other modules**, rather than discarding the edits or treating temporary proportional hide-expansion as permanently saved widths. Re-showing modules may change **rendered pixel widths** through responsive recomputation; the user-modified relative/intended widths must survive. **No implicit write to browser-local named layouts**; storing the edited arrangement remains an explicit user action. Question 50 choice A fixes the ratio mapping rule described above; implementation must still verify subpixel rounding, minimum-clamp behavior and intended-weight normalization against these acceptance rules.
- **Right-neighbor minimum boundary — owner choice A (approved):** when increasing the selected module would make its immediately adjacent visible **right-hand** module smaller than its approved minimum (e.g., Spectrum reaching **200 CSS px** when expanding Waveform), **stop the shared divider at that limit**. Do not continue dragging by taking width from modules farther to the right, increasing strip overflow/scroll width, hiding anything or violating the neighbor's minimum. Apply the reciprocal minimum guard when shrinking the selected module itself. This is the same two-module resize interaction, not a new resize mode.
- **Rightmost visible module — owner choice A (approved):** resize the rightmost module (e.g., **Oscilloscope** in Balanced) by dragging its **left-hand shared divider**, between it and the immediately adjacent **visible module to its left** (e.g., Output Meters). Only those two modules change widths by equal and opposite amounts: moving the divider left enlarges the last module while narrowing its left neighbor; moving right does the reverse. The same approved per-module minimums and stop-at-minimum rule apply to **both** modules. This does **not** add an independent draggable outer-right edge or extend horizontal overflow to grow the last module.
- **Only one visible module — owner choice A (approved):** when the user has intentionally hidden the other six modules, **the remaining visible module expands automatically to the full usable horizontal width** of the strip's module area. No independent draggable outer-right edge, dedicated width slider or numeric size control is added for this one-module state; the normal shared-divider drag is unavailable because it has no neighbor. This is the one-module case of the already approved proportional redistribution after hiding modules, **not** a change to the module's underlying intended/saved width.
- **Single-module minimum and restoration:** continue to enforce that module's previously approved minimum CSS width; if its minimum cannot fit inside the usable inner viewport width, let the strip scroll horizontally rather than squeezing the sole module below minimum. Keep every hidden module's intended width/settings intact, so that re-enabling any other module recomputes the regular visible proportions from underlying intended values (no drift from the temporary full-width state). Do not overwrite custom browser-local presets, change strip height/audio capture, or modify Balanced/Beatmaking/Mixing/Live built-in widths. When the last module is intentionally hidden, follow the approved **zero-visible-module auto-collapse choice C** below; no empty expanded strip.
- **All modules hidden — owner choice C (approved):** if the user explicitly hides the **last remaining visible module**, there are **zero** visible modules and the **entire Visuals strip automatically collapses**. Leave a discoverable, focusable/keyboard-accessible **restore affordance** available while Visuals remains open. Do not leave an empty, expanded meter strip, prohibit hiding the final module, delete any module, close Visuals, or automatically switch to a different preset. Do not confuse this user-triggered all-hidden collapse with responsive auto-hiding or user-initiated whole-strip collapse.
- **All-hidden restoration — owner choice A (approved):** the remaining collapsed-strip **restore control opens a selector listing all seven available Visuals modules** (Waveform, Spectrum, Spectrogram, Loudness, Stereo Meter, Output Meters, Oscilloscope), without first expanding an empty strip or restoring a whole preset. **Only when the user explicitly selects one module** should the strip expand and show that chosen module. Until selection (including dismiss/cancel), keep the zero-visible state collapsed; do not auto-enable any meter. That initially sole visible module fills usable horizontal width under the separately approved single-module rule (subject to its minimum/scrolling). Other six modules remain hidden but available for later explicit reveal.
- **All-hidden restoration affordance position — owner question 53 choice A (approved):** while Visuals remains open with **zero visible modules and the strip auto-collapsed**, show a **small, visibly discoverable tab horizontally centered at the bottom edge of the K.O. Tool browser viewport** (not on the physical OS screen and not an OS-global overlay). Activating the tab via **pointer, touch or keyboard** opens the **seven-module selector directly above that tab**, inside the browser viewport. Do **not** first expand an empty strip or automatically restore any module/preset. If dismissed without selection, the selector closes, the tab remains available, and the strip remains collapsed with zero modules visible and auto-hide OFF (question 52). Only explicitly choosing one listed module expands the strip with that module alone; capture stays stopped until separately started (question 48). Keep the tab focusable, accessibly named and reachable without relying on hover; restore the interaction path for keyboard users on picker dismissal. Do not silently alter layouts, intended widths, preferred session height, selected audio source or stored presets. Question 55 choice A extends this **same tab placement** to explicit manual whole-strip collapse with one or more selected modules; the behavior is immediate populated-strip expansion instead of opening the picker. Exact tab dimensions/colors and picker focus/scroll ergonomics remain implementation details.
- **Shared bottom-center restore tab for manually collapsed populated strips — owner question 55 choice A (approved):** reuse the **same small restore tab centered along the bottom edge of the K.O. Tool browser viewport** for both complete-collapse states. When the user has **manually collapsed the whole strip while at least one module remains selected/visible in the underlying layout**, activation by **pointer, touch or keyboard** **immediately re-expands the existing populated strip** with exactly its prior visible-module membership, order and intended widths: **do not show the seven-module selector**, turn on hidden modules, load a new preset, or force the sole-module recovery flow. When **zero modules are visible**, activation of **the same tab** instead opens the approved seven-module picker **directly above it**, which stays scrollable in constrained viewports (questions 53–54). This is a **state-dependent action on one shared tab**, not an additional bottom-right button or reliance on re-clicking the desktop icon. In both states, collapse already turned optional pointer auto-hide **OFF** (questions 51–52): reopening must leave it OFF, so the strip remains continuously visible until explicitly changed. Per question 48, complete collapse already stopped Visuals-owned capture tracks: tab activation must **never automatically restart capture**. Preserve the selected audio-input preference, same-session preferred height, module settings, browser-local named presets and unsaved edits. The tab should remain accessible and discoverable until explicit restoration. This shared-placement rule does **not** replace the distinct temporary pointer-triggered auto-hide reveal behavior (which may retain permitted active capture). Exact tab sizing, visual label/appearance, focus behavior and pathological viewport accommodations remain design/implementation validation.
- **Constrained-viewport seven-module picker — owner question 54 choice A (approved):** the selector remains a **single vertical list anchored immediately above the centered bottom-edge restore tab** even when the K.O. Tool browser viewport is too short/narrow to display all seven entries at once. **Limit the selector's rendered height to the space actually available above the tab within the browser viewport** (including needed surrounding clearances), keep the **tab fixed and accessible**, and make the **list itself vertically scrollable** to reach every one of the seven module options. When all seven fit, no scrolling is necessary. **Do not replace the selector with a multi-column grid or a full-viewport/full-screen picker**, do not move the tab or let the list spill outside the K.O. Tool browser boundary, and do not expand an empty Visuals strip until an explicit module selection. Support scrolling and selection through **touch, mouse wheel/trackpad and keyboard** with an accessible focus/interaction path; never clip the first/last options irretrievably or hide the dismiss path. Cancel closes only the selector, keeping zero modules visible, the strip collapsed, auto-hide OFF, and capture stopped. The exact padding, min touch/keyboard target dimensions, focus order, scrollbar appearance and pathological viewports too short for even a usable list item require implementation/accessibility verification rather than an invented fixed CSS-pixel breakpoint. Technical references: [MDN `overflow-y`](https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/Properties/overflow-y) and [MDN `max-height`](https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/Properties/max-height).
- **Recovery state protection:** the picker and chosen-module restore retain each hidden module's intended width/order/settings and all browser-local custom presets. Restoring one chosen module must not silently restore the prior Balanced/Beatmaking/Mixing/Live preset or overwrite the custom layout. An all-hidden collapse, opening/dismissing the selector and selecting a module must not reset the session's preferred strip height or replace the selected audio source/permissions. Under the separately approved question 48 choice C, the all-hidden collapse **stops active browser audio capture**. Opening/dismissing the selector or selecting a module does **not** automatically restart it; capture resumes only after the user's explicit action. Preserve the selected-input preference and do not infer that existing browser permissions are revoked or guaranteed to remain valid. The **bottom-center tab and above-tab picker placement** are settled by question 53 choice A; exact styling, tiny-viewport fit and focus behavior remain for separate design. Question 55 choice A assigns **the same bottom-center tab** to manual collapse with visible modules, but it **directly restores** those modules instead of opening the all-hidden picker.
- **Still open:** exact shared tab/picker dimensions, styling, focus order and accessibility testing under pathological viewport dimensions. **Question 53 fixes the bottom-center anchor, question 54 fixes the constrained-height vertically scrollable all-hidden selector, and question 55 fixes state-dependent actions of the shared tab.** Minimum-bound pixel rounding, question 50 ratio normalization under extreme constraints and other responsive accessibility details remain engineering work. The two-visible-module-only manual edit semantics are approved.
- This is the *default starting arrangement*, not a ban on user customizations or replacement of the three separate workflow presets (beatmaking, mixing, live filming). Restoring defaults should recover the Balanced composition without overwriting user-saved presets.

## Configurable strip and presets — owner choice C (approved)

The bottom meter strip is a **customizable modular workspace**:

- **Reorder:** drag modules left or right, preserving the user's selected order.
- **Resize module widths — owner choice A:** drag a shared divider between a selected module and its immediate visible right neighbor; the two widths change by equal and opposite amounts within approved minimums, while all other modules retain their intended widths. **Stop at either affected module's minimum (neighbor-boundary choice A)**, without taking width from farther modules. For the rightmost visible module, use the shared **left-hand divider** with its immediately adjacent visible left neighbor (rightmost choice A); if **one** module is visible, let it automatically fill the available horizontal space without any standalone width drag/control (single-module choice A); its module minimum and restoration of hidden modules' widths remain binding.
- **Resize the entire strip's height — owner choice B (approved):** the user may drag the **top border/resize handle** of the bottom-docked strip **up or down** to freely adjust its height. **Do not require Compact, Standard or Expanded height presets**; those options were explicitly not selected. The lower edge remains docked to the bottom of the K.O. Tool browser viewport while the upper edge moves.
- **Owner-approved height bounds — choice A:** resize the strip between a **minimum of 90 CSS px** and a **maximum of 40% of the K.O. Tool browser viewport's CSS height** under normal viewport conditions. **Exception confirmed, owner choice A:** whenever the viewport is **shorter than 225 CSS px**, the **90 CSS px minimum has priority over the 40% maximum**. The strip may temporarily occupy more than 40% of a very short browser window. The bottom edge remains docked; do not automatically collapse/hide the strip or force it below 90 px merely to honor 40%. Maintain discoverable controls, legible meters and access to other K.O. Tool content where feasible; this exception does not authorize a host-OS overlay.
- **Normal launch height:** start at **150 CSS px when it fits** within the approved height bounds. For a viewport between **225 and 375 CSS px high**, 40% of the viewport is between 90 and 150 px, so the launch height needs to be **constrained by the 40% maximum**. Do not overwrite the 150 px standard or the session-only height rule.
- **Short-viewport behavior is settled:** at a viewport of 200 CSS px high, 40% would be 80 px, so the strip's approved minimum remains **90 CSS px** instead. At exactly 225 CSS px, the minimum and cap coincide at 90 CSS px. The visual treatment of exceptionally tiny windows (e.g., when the whole viewport is shorter than 90 px), keyboard access and potential scrolling must be verified during implementation; do not misrepresent physical layout feasibility.
- **Behavior while resizing:** all seven available modules remain selectable and the current visible layout/order is preserved. Visualizations should reflow/re-render to the new height without falsely reporting new audio measurements or breaking input capture. Ensure pointer/keyboard/touch interaction and discoverability are considered during implementation.
- **Owner-approved height reset choice A:** vertical resize affects only the **currently open Visuals session**. When the Visuals app is closed and reopened, or K.O. Tool reloads and Visuals opens again, the strip returns to its **approved standard launch height of 150 CSS px** (owner standard-height choice B). **Do not persist user-adjusted height** as a browser-global preference or in any saved custom layout/preset. Layout loading on a later launch must restore the chosen modules/order/widths, **not the old height**.
- **Switching layout presets within one open Visuals session — owner choice A (approved):** **preserve the current user-adjusted height** when switching between built-in Beatmaking/Mixing/Live layouts, Balanced, and browser-local custom layouts. Switching a preset may change module selection, visibility, order and widths, **not the entire strip height**. If the browser viewport changes, honor the approved 90 CSS px / 40% limits where simultaneously satisfiable; preset switching alone must never reset height to 150 CSS px or load a preset-specific height.
- **Viewport shrink/recovery — owner choice A (approved):** within one open Visuals session, keep a **session-only preferred height** representing the user's most recent manual height selection (or the initial 150 CSS px before any manual drag). When the browser viewport shrinks, **temporarily clamp only the displayed height** to the current approved bounds; do **not overwrite** the preferred height just because the viewport became smaller. When the viewport grows again, **automatically restore the preferred height as far as the current bounds permit**, without making the user drag again. Example: in an 800 CSS px-high viewport a user sets **250 CSS px**; at viewport height 500 CSS px, the display clamps to **200 CSS px** (40%); restoring the viewport to 800 CSS px returns the strip to **250 CSS px**.
- **Manual changes still win:** if the user explicitly drags the strip while the viewport is constrained, **that drag establishes a new preferred height** for the remainder of the session; later enlargement restores the *new*, not the older, manually selected value. Switching layout presets does not replace this preference. At very short heights below 225 CSS px, the already approved **90 CSS px minimum takes priority** over the 40% cap; preserving controls in exceptionally tiny windows requires implementation validation.
- **Session boundary:** the preferred height is **in-memory only**, is not part of saved browser layouts or global settings, and **resets to the approved 150 CSS px launch target** on Visuals close/reopen or K.O. Tool reload. No compulsory Compact/Standard/Expanded modes or native fullscreen mode are implied.
- **Show / hide / restore:** temporarily remove individual modules from view without removing their feature or input configuration. Make all seven discoverable and restorable.
- **Built-in layout presets:** offer starting arrangements for **beatmaking**, **mixing**, and **recording/filming live performances**. Approved built-in compositions and widths are **Beatmaking composition/widths (choice B), Mixing composition (choice A) and widths (choice B), Live composition (choice B) and widths (choice A)**. These remain separate from the Balanced default and browser-local custom layouts.
- **Beatmaking preset — owner choice B (approved):** show **exactly five modules initially**, left to right: **Waveform → Spectrum → Spectrogram → Output Meters → Loudness**. **Stereo Meter** and **Oscilloscope** are **hidden in this built-in layout**, not removed from Visuals or disabled globally; users can reveal either, drag/reorder modules, adjust widths and explicitly save their own custom configuration.
- **Beatmaking scope/behavior:** activating the built-in preset restores that five-module selection and order without overwriting Balanced or any browser-local custom layout. The preset switch **does not reset the currently chosen strip height**, change audio input/capture, clear saved presets or alter Auto Theme. All five modules retain their already approved minimum widths (Waveform/Spectrum 200 CSS px each, Spectrogram 160 CSS px, Output Meters/Loudness 96 CSS px each); their sum is **752 CSS px before actual gaps, borders, padding and controls**. **Beatmaking width proportions — owner choice B (approved):** at sufficient available width, the five visible modules have intended relative widths **Waveform 35%; Spectrum 30%; Spectrogram 15%; Output Meters 10%; Loudness 10%** in the preset's approved order. **35 + 30 + 15 + 10 + 10 = 100%.** These targets belong to **Beatmaking only**; Balanced keeps its distinct 25/25/18/8×4 split. At narrower widths, enforce each module's previously approved minimum and enable horizontal scrolling if the visible minimums plus gaps/controls exceed the available inner width; do not force the 15% Spectrogram below 160 CSS px or silently modify saved presets. Manual pairwise drag, optional hide/show with proportional redistribution and restoring Beatmaking's defaults continue to work; preset switching must not reset strip height or input.
- **Mixing preset — owner composition/order choice A (approved):** show **exactly six modules initially**, in this left-to-right order: **Output Meters → Loudness → Spectrum → Stereo Meter → Spectrogram → Waveform**. **Oscilloscope is hidden only in this built-in preset**; it stays available for manual reveal. No other module should be omitted, reordered or changed to a different module without the user explicitly customizing their layout.
- **Mixing behavior and constraints:** switching into Mixing or restoring its built-in defaults recovers the six-module selection/order, without altering Balanced, Beatmaking or browser-local user presets; manual drag-reordering, independent per-module hiding/reveal and explicitly saved personal layouts remain supported. Switching layouts does **not** reset the current session's strip height, selected audio input/capture or Auto Theme. Honor all approved per-module minimum widths (Output Meters 96 CSS px + Loudness 96 + Spectrum 200 + Stereo Meter 96 + Spectrogram 160 + Waveform 200 = **848 CSS px** in total before real gaps/borders/controls/padding); use horizontal scrolling when required. **Mixing width proportions — owner choice B (approved):** when the six modules are visible with sufficient space and no user override, use **Output Meters 20%; Loudness 20%; Spectrum 20%; Stereo Meter 20%; Spectrogram 10%; Waveform 10%**, in approved left-to-right order. Check **20 + 20 + 20 + 20 + 10 + 10 = 100%**. These are **Mixing-specific preferred ratios**, not pixel minimums, and do not modify the Balanced or Beatmaking targets. At **2,000 CSS px of usable module-content width**, before gaps/controls, the target widths are **400 / 400 / 400 / 400 / 200 / 200 CSS px**: every minimum fits. At narrower widths, do not force Spectrogram's 10% below **160 CSS px** or Waveform's 10% below **200 CSS px**; honor all six approved minimum widths, redistribute or scroll horizontally when necessary, without hiding extra modules, changing their order or overwriting custom presets. Continue to permit manual pairwise resizing and deliberate show/hide; switching presets does not reset strip height or audio source.
- **Live preset — owner composition/order choice B (approved):** show **exactly five modules initially**, left to right: **Waveform → Spectrum → Spectrogram → Oscilloscope → Output Meters**. **Stereo Meter** and **Loudness** are hidden **only in this built-in Live layout**, not removed from Visuals or disabled elsewhere; users may reveal either, change the order, adjust widths and explicitly save a personal preset. This selection prioritizes moving sound displays for filming live performances; it is **not** authorization for recording/export or an OS-global video overlay.
- **Live behavior and constraints:** applying or restoring built-in Live recovers the chosen five-module visibility/order without rewriting Balanced, Beatmaking, Mixing or browser-local user layouts. ## Technical boundary and external sources

Current repository `main` contains a SpeedUpperCut audio converter and My EP (Web MIDI/SysEx) but no Visuals app or verified browser audio-capture implementation. It is not valid to infer a supported EP USB-audio stream from a firmware changelog alone.

Relevant standard web APIs (prospective implementation, **not current code**):

- [MDN `MediaDevices.enumerateDevices()`](https://developer.mozilla.org/en-US/docs/Web/API/MediaDevices/enumerateDevices): lists permitted hardware audio input devices, subject to permissions and secure context; some labels/devices remain hidden until permission is granted.
- [MDN `MediaDevices.getUserMedia()`](https://developer.mozilla.org/en-US/docs/Web/API/MediaDevices/getUserMedia): asks permission for a requested audio input and yields a `MediaStream` when supported. Explicit user permission and secure context (HTTPS/`localhost`) are required.
- [MDN `MediaStreamTrack.stop()`](https://developer.mozilla.org/en-US/docs/Web/API/MediaStreamTrack/stop): stops an acquired track (`readyState` becomes `ended`); it cannot later be restarted by merely showing the Visuals strip. This API does not guarantee that another app/tab has stopped using the same underlying physical device.
- Web Audio analysis can consume a granted media stream, but the exact pipeline, latency, quality, DSP visualization and browser support are still design/implementation work.
- **USB Audio, Web MIDI, and device FILE/SysEx are separate interfaces.** Do not promise cross-OS simultaneous performance or assume device exposure just because My EP connects.

## Proposed UX contract (to validate before implementation)

- Opening Visuals shows a clear **Select audio input** control and idle state; no permission prompt or audio recording without an explicit user action.
- After permission is granted, list available browser audio inputs with names when permitted, including the EP if the OS and browser expose it.
- Switching inputs must stop the previous media track and release any unused audio stream; do not leave microphone capture running after **manual collapse or all-hidden auto-collapse**. Only temporary opt-in pointer auto-hide intentionally keeps previously authorized capture active, with discoverable status and a Stop action (question 48, choice C).
- Clearly handle permission denied/revoked, no available device, unplugging EP/interface, OS device change, tab hidden, and browser loss of capture.
- When an audio input is missing/unsupported, display an explanation and possible corrective action, not a fake animation falsely labeled as live audio.
- Independently of My EP connection, users should be able to use Visuals with another selected audio interface or microphone, where the browser supports it.
- Performance graphics should favor smooth response, legibility from a camera, restrained CPU load, and a non-distracting presentation.

## Verification and acceptance plan (future code authorization required)

| Scenario | Expected |
| --- | --- |
| No EP, supported microphone / audio interface | Explicit permission then live visualization from chosen input |
| EP present as browser `audioinput` | EP selectable, input works if actually exposed and authorized |
