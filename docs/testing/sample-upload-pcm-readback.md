## Result contract

`sampleUploadController` passes final `prepared.data` to PUT, including the result of `prepareMyEpRepitchSample` when enabled. After existing INFO/metadata/path/size/name/channel/rate checks it uses `verifySamplePcm` to GET the full destination through the same strict FILE lease and compare length and every byte. COPY shares that helper and retains its existing error, safety and rollback policy from [6cb59c9 / ZAT-59](https://github.com/Zatumanen/Ko-tool/commit/6cb59c9df6931b0d33fde1fda8b92eec5f877f94).

Only completed verification and transaction finalization permit Store `ready/verified`, WRITTEN, timing publication and the next PUT. Global progress reserves 35% for preparation, 50% for upload, 14% for PCM readback and the remainder for completion; `verifyingMs` includes the existing checks plus PCM GET/comparison. These weights are UI phases, not hardware time predictions. A full GET adds one sample-sized transfer per successful upload.

An unverified readback stops the batch, preserves the written slot, propagates failure through the recovery journal and activates the existing safety lock when the original session is still current. If the transport has already invalidated the session token with a safety lock, the authoritative runtime connection epoch permits recording UNVERIFIED only for that same device connection; reconnect/replacement advances the epoch and cannot be repainted by the old upload. No automatic DELETE, retry or rollback is added for this state. Session replacement prevents old FILE calls and Store updates. Delayed hydration, FILE events and operation cleanup cannot promote failed PCM. Legacy pre-readback per-file handling remains: preparation failure or a clean rejected creation can allow the next file; the existing guarded rollback is not used for PCM/session ambiguity, and a failed rollback stops the batch. Prior verified successes remain in the result.

Its UTF-8 bytes exactly match the registry: **1,800,331 bytes**, SHA-256 `d032b3a1d9398663f313c54b671e366c5625f3612a2285ceaacad636cb5d7a98`. Searchable symbols and zero-based UTF-16 offsets: `SysExFileHandler.put` 841305, `uploadSound` 1159319, queue's awaited call 1152286, `getSound` 1168094, event listeners around 1495692. Source map is absent. Existing five WASM hashes also match U03–U07; binaries were neither executed for this comparison nor changed.

The live official page pointed to `index-mzHAnDsS.js` (1,795,551 UTF-8 bytes, SHA-256 `ad10f8c52b03f1a94bc341321c53719ef8894f5be3add3e9f8b73dd6d530f847`); the inspected upload/put chain has the same completion sequence. This is static evidence, not confirmation of firmware behavior or event ordering on hardware.

## Remaining hardware evidence

Static code establishes the official completion condition. To observe runtime ordering, a separately authorized DevTools scenario would upload one short synthetic WAV into a free expendable slot, without preview/download. Capture Web MIDI send/midimessage plus the queue complete transition: PUT 02 00/02 01 and empty EOF, SET 07 01, INIT 01, ADDED/UPDATED, INFO 0b, metadata GET 07 02 and any PCM GET 03 00/03 01. A network HAR alone does not capture MIDI. Redact serials/names and replace PCM with lengths/hashes while preserving request correlation, mapped slot IDs, page counts, statuses, exact model/firmware and timestamps. No such hardware scenario was executed or authorized by this software change.
